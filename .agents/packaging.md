# Packaging and release builds

## Recipes

| What? | Where? | Built by |
| --- | --- | --- |
| Arch | `packaging/PKGBUILD` | `makepkg`, from the working tree as it is |
| Debian 13 | `packaging/debian/` | `dpkg-buildpackage`, after copying the directory to the repository root |
| Fedora 44 | `packaging/fedora/snipshot.spec` | `rpmbuild`, from a `git archive` of `HEAD` named `snipshot.tar.gz` |
| Alpine 3.24 | `packaging/alpine/APKBUILD` | `abuild`, from a `git archive` of `HEAD` |

makepkg and abuild both create `src/` and `pkg/` beside their own recipe, so neither can sit at the root
and they cannot share a directory. dpkg-buildpackage only looks for `debian/` at the root, which is why
CI copies it there rather than the recipe living there. `debian/changelog` is generated by the workflow
because it only carries the version. The spec and the APKBUILD only ever see committed files, while
makepkg and dpkg-buildpackage build whatever is in the tree.

Qt comes from the distribution, so each package is built for one release, which is why there is one
Debian and one Fedora package rather than one per format family.

Runtime dependencies are written by hand on top of what each tool derives from the binary's libraries:
the QML modules, the Wayland platform plugin, LayerShellQt's shell integration plugin and every external
tool are all found at runtime. Fedora names QML modules by their `qt6qml(...)` provides. Alpine has every
QtQuick module in `qt6-qtdeclarative` and the Wayland platform plugin in `qt6-qtbase-x11`, which
`libQt6Gui` already pulls in.

| What? | Arch | Debian 13 | Fedora 44 | Alpine 3.24 |
| --- | --- | --- | --- | --- |
| Qt Multimedia's FFmpeg backend | `qt6-multimedia-ffmpeg` | in `libqt6multimedia6` | in `qt6-qtmultimedia` | `qt6-qtmultimedia-ffmpeg` |
| An OCR language | `tesseract` needs a `tessdata` | `tesseract-ocr` pulls English | `tesseract-langpack-eng` | `tesseract-ocr-data-eng` |
| Hardware encoded recording | `gpu-screen-recorder`, optional | none | none | none |

Without gpu-screen-recorder, `wf-recorder` is the only recorder, and it stays optional like `ffmpeg`.
Fedora recommends `/usr/bin/ffmpeg` rather than a package, so `ffmpeg-free` and RPM Fusion's `ffmpeg`
both satisfy it. Alpine has no optional dependencies, so it leaves recording tools to the user.

`gtk3` came over from the PKGBUILD into every recipe, though nothing in the source references GTK. Drop
it from all four together if it turns out to be stale.

## Version

`packaging/version.sh` is the one place a package version comes from. It runs `git describe` against the
latest `v*` tag, so the rolling `experimental` tag never becomes a version, and prints `0.0.1.r2.g085e6ec`
for two commits past `v0.0.1`. Arch, Debian and Fedora use it as it is. apk versions cannot carry a hash,
so the APKBUILD turns it into `0.0.1_git2`. Every checkout that builds a package therefore needs the full
history and its tags, which is what `fetch-depth: 0` is for.

`project(SnipShot VERSION ...)` in `CMakeLists.txt` is what the app reports about itself, and it has to
match the tag.

## Zig

Packages build with Zig 0.17.1, the floor `AGENTS.md` sets. 0.18-dev has to keep building too. Arch
x86_64 ships 0.17.1, but Arch Linux ARM, Fedora 44 and Alpine 3.24 ship 0.16 and Debian 13 has no Zig at
all. So every job gets it from `mlugg/setup-zig`. There is no `build.zig.zon` for it to read the version
from, so `ZIG_VERSION` at the top of `ci.yml` and `build-packages.yml` carries it, and the two move
together. Only the PKGBUILD lists `zig` as a dependency. The Arch job installs everything else from the
PKGBUILD's own arrays and builds with `--nodeps`. setup-zig points both Zig cache variables at root's
home, so the job hands that directory to its unprivileged builder.

Zig's release builds are static, so the Alpine job mounts the one setup-zig put on the runner into the
container rather than downloading a second copy.

## Workflows

`.github/workflows/build-packages.yml` builds all four formats, each on a native x86_64 and aarch64 runner.
It is reusable and has no triggers of its own, so the build steps have one owner. `release.yml` calls it
for a tag beginning with `v` and creates or updates that tag's GitHub release with a `SHA256SUMS`. A manual
run only stores workflow artifacts. `experimental.yml` calls it for a push to `main` and deletes and
recreates the rolling `experimental` pre-release, so GitHub lists it above the tagged releases.

It skips whatever cannot change a package. A push confined to `**.md` or `.agents/` never starts, and one
whose tip message begins with `docs` or `build: release` stops at the `build` job, so a release is built
once from its own tag instead of twice.

`ci.yml` builds and runs the tests on every push and pull request, on Debian 13 for Qt 6.8, the oldest
supported, and on Fedora 44 for the newest. It installs build dependencies straight from the recipes
(`apt-get build-dep ./packaging` and `dnf builddep` on the spec), so those lists are only written once.

Arch has no ARM port of its own, so the aarch64 half of the Arch job builds against Arch Linux ARM through
`menci/archlinuxarm:base-devel`, which is rebuilt daily where the alternatives have gone stale. Arch Linux
ARM still compresses packages with xz, so the job rewrites `PKGEXT` and both architectures come out as
`.pkg.tar.zst`. Both halves pass `--disable-sandbox`, because pacman's download sandbox wants a Landlock
ruleset a container cannot set up.

The Alpine job does not use a job container. Every action is Node, the runner's Node is linked against
glibc, and a musl job container fails at `actions/checkout`. It checks out on the runner and builds inside
`docker run alpine:3.24`. abuild signs with a key it generates on the spot, so the package installs with
`apk add --allow-untrusted`. It also writes the architecture into a directory rather than the file name,
so the job renames each package before uploading.

Uploads leave out debug packages: Arch's `-debug`, Debian's `-dbgsym` and Fedora's `-debuginfo` and
`-debugsource`.

## Cutting a release

One commit, `build: release <version>`, that bumps `project(SnipShot VERSION ...)`. Then an annotated tag
on it, `git tag -a v<version> -m "SnipShot <version>"`. Push `main` before the tag, or `release.yml` fails
its `--verify-tag`:

```sh
git push origin main && git push origin v<version>
```
